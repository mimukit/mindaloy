## Context

Mindaloy is a standalone spaced repetition web app for English-speaking learners and developers. It exposes APIs so agents and other systems can manage cards and use review results. The product name is confirmed.

The earlier plan makes the learning repository the database. That design ties the app to one repository and one integration. Mindaloy owns its data instead. The learning repository becomes an optional API client.

Success means a user can create cards through an external client, review them in the web app, and read the resulting progress through the API. No step requires the learning repository. Agent access must support the same core operations as the web interface.

Phone reviews, offline use, typed answers, and stable card IDs come from the earlier discussion. This draft retains them as proposed first-version requirements. The user has not approved the complete feature scope.

The project starts in an empty folder. At plan creation, it has no application code, database, Git repository, remote, or deployment configuration. The visual work now supplies DESIGN.md and approved collection and review references. Integration settings still need a reference. ## Approach

Recommend one backend, one relational database, and a web client. The backend owns cards, review records, and schedules. The web client uses the same service operations as external clients. This keeps scheduling and permissions consistent.

The smaller alternative is an online-only app. It removes offline synchronization from the first release, but it postpones the phone review goal. The larger alternative adds lessons, learning phases, and agent workflows inside Mindaloy. It expands the product before the card review process has real use. The lateral alternative is an API service with a reference client. It supports integrations but leaves the desired review interface to another system.

Recommend the standalone app with offline reviews. Keep lesson planning in external systems for the first release. Confirm both recommendations in phase 1.

### Proposed technical decisions

These choices support a coherent draft. They are recommendations, not user-approved decisions.

| Area | Proposed choice |
|------|-----------------|
| Application structure | Use TypeScript for the API, web client, and shared request schemas. Choose the frameworks in phase 1. |
| Storage | Use PostgreSQL for accounts, collections, cards, reviews, and sync metadata. |
| API contract | Define a versioned HTTP JSON API with an OpenAPI specification. Keep internal data fields out of the public contract. |
| Access | Use browser sessions for the web app and revocable API keys for external clients. Scope keys by operation and collection. |
| Ownership | Give each collection one owner. Check ownership on every request. Defer shared collections. |
| Cards | Assign stable server IDs. Support an external source ID and external card ID within each collection. |
| Reviews | Store immutable review events with unique client event IDs. Keep schedules as derived state. |
| Scheduling | Use FSRS through one server scheduler. Store the scheduler version and settings needed to reproduce results. |
| Offline client | Use a PWA with IndexedDB for cached cards and pending reviews. Treat local schedules as provisional until sync. |
| API tests | Use Vitest with an isolated PostgreSQL test database for ownership, retry, and scheduling checks. |
| Browser tests | Use Playwright for review, offline, and sync checks. Use accessible locators. |
| UI rules | No house rules or approved reference exist. Approve mobile layouts, keyboard behavior, and a visual reference before UI implementation. |

### Phase 2: define the data model and API contract

- Define accounts, collections, cards, immutable reviews, and derived schedules.
- Give cards a cue, key points, archive state, revision, and optional source reference.
- Define list, create, read, update, and archive operations for collections and cards.
- Define due-card queries, review submission, review history, and progress queries.
- Define API key creation, scope selection, revocation, and last-use information.
- Define pagination, request validation, error codes, and retry behavior in the OpenAPI specification.
- Define idempotent card creation through external IDs. Define idempotent review submission through client event IDs.
- Define card revision checks and the order for reviews from multiple devices.

Done when: The contract covers an external client's complete create, review, and progress process. Examples include unauthorized access, duplicate requests, and conflicting card edits.

### Phase 3: build storage, access, and card management

- Create the application structure and database migrations from the approved decisions.
- Implement account access, browser sessions, and API key authentication.
- Store API key hashes. Return each new key value only when the user creates it.
- Enforce ownership and key scopes before reads and writes. Limit request rates and batch sizes.
- Implement collection and card operations with external ID support and revision checks.
- Keep credentials and typed answers out of routine request logs.

Done when: API tests create a card through a scoped key and read it through its owner's session. Another account cannot access it. A revoked key fails, and repeated external IDs do not create duplicate cards.

### Phase 4: implement reviews and scheduling

- Implement the approved scheduler and grade mapping in one server module.
- Store each accepted review with its event ID, card revision, review time, and grade. Store the typed answer if phase 1 approves retention.
- Persist the review event and derived schedule in one database transaction.
- Rebuild schedules from review events and recorded scheduler settings.
- Return due cards, review history, and defined progress measures through the API.
- Preserve review history when a card is archived. Apply the approved policy when card content changes.

Done when: Tests confirm deterministic replay, duplicate protection, and preservation of concurrent review events. Time zone tests follow the approved rule.

### Phase 5: build the web review process

- Implement the approved collection list, card editor, review screen, and integration settings.
- Show the cue before the answer. Let the user type an answer and reveal the key points.
- Let the user compare the answer with the key points and select an approved grade.
- Show due counts, review results, and clear states for an empty queue or failed request.
- Let the user create and revoke API keys with visible scopes.

Done when: A browser test creates a collection, reviews a card, reloads the page, and reads the saved result. The review process supports a phone viewport and keyboard use.

### Phase 6: add offline reviews and reliable sync

- Cache the application and selected card collections for offline use.
- Save pending reviews in IndexedDB before advancing the review screen.
- Show pending review counts and whether the displayed schedule is provisional.
- Sync pending events with stable event IDs. Keep events until the server confirms receipt.
- Apply server schedules after sync. Explain rejected reviews without discarding the user's answer.
- Handle card revisions, archived cards, expired sessions, and interrupted sync through the approved rules.
- Separate cached data by account. Prevent a later account from viewing another account's data on the device.

Done when: A browser test reviews cards offline, reloads, reconnects, and retries an interrupted sync. The server stores each review once. A device test confirms the same process on the owner's phone.

### Phase 7: prove external integration and prepare deployment

- Build a small documented API client that does not read the learning repository.
- Use it to create cards, update one card without duplication, and read review results.
- Document account setup, API keys, examples, local development, and deployment.
- Document database backup, restore, schema migration, and service rollback procedures.
- Test a database restore into an isolated environment.
- Prepare a deployment configuration and a release checklist. Record phone checks that need the owner.

Done when: The independent client completes the create, update, review, and progress process against a clean test deployment. The documented restore recovers cards and review history. The configuration is ready for a separate deployment approval.

## Migration and rollback

The first release starts with an empty database. It does not move or modify data in the learning repository. A future tutorkit client must use the public API and stable external IDs.

Add database migrations from phase 3. Test them before deployment. Back up stored data before a migration that can remove or rewrite it. Record which application versions support each schema.

During phase 6, keep unsent reviews until the server confirms them. An application update must preserve the pending queue. A service rollback must preserve accepted review events and avoid replaying them as new events.
