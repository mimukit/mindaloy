# Plan: Mindaloy standalone learning app

Grilled: 2026-10-22

Created: 2026-10-21

Status: Scope, stack, and scheduling rules approved in phase 1 (#1). The visual reference is still open in #2.

## Context

Mindaloy is a standalone spaced repetition web app for English-speaking learners and developers. It exposes APIs so agents and other systems can manage cards and use review results. The product name is confirmed.

The earlier plan makes the learning repository the database. That design ties the app to one repository and one integration. Mindaloy owns its data instead. The learning repository becomes an optional API client.

Success means a user can create cards through an external client, review them in the web app, and read the resulting progress through the API. No step requires the learning repository. Agent access must support the same core operations as the web interface.

Phone reviews, typed answers, and stable card IDs come from the earlier discussion. The first release reviews on a phone through the browser while it is online. Offline review moves to a later release.

The repository holds this plan, `CONTEXT.md`, and the ADRs under `docs/adr/`. It has no application code, database, or deployment configuration yet. No DESIGN.md or approved visual reference exists; #2 tracks the reference. The source plan remains at `/home/dev/projects/learning/docs/plans/0001-plan-recall-pwa-2026-10-17.md`.

## Design decisions (settled)

| Decision | Resolution |
|----------|------------|
| Product name | Mindaloy. Use the same spelling in the app and documentation. |
| Product boundary | Build a standalone web app with APIs for external systems. |
| Repository dependency | No runtime dependency on the learning repository or its Markdown formats. |
| Agent access | Treat external clients as supported users of the core API. |
| Audience and tone | Address English-speaking learners and developers. Use a playful product name. |
| Planning scope | Write a draft only. Do not create application code, GitHub issues, or deployments. |
| Offline reviews | Not in the first release. Phones review through the browser while online. Offline review with sync is a later release. Review submission still requires a `client_event_id`, so offline can come later with no contract change. |
| Account model | One owner per deployment, created by `pnpm db:seed:owner` from `OWNER_EMAIL`. Sign-up is off from the first deploy. The data model and ownership checks still support more accounts, and tests create a second account directly. |
| Lesson planning | Stays in external systems. |
| Typed answers | Stored on the review as optional `typed_answer`, up to 4,000 characters, with no time limit. Deleted only with its card, collection, or account. Never written to request logs. Returned in review history to the owner session and to keys with `reviews:read`. |
| Change delivery | External clients poll the list endpoints with an `updated_since` cursor. No webhooks in the first release. |
| Default API key scope | A new key covers the collections the owner picks at creation. Default operations: `collections:read`, `cards:read`, `cards:write`, `reviews:write`, `reviews:read`, `progress:read`. Opt-in: `cards:archive`, `collections:create` (a key with it gets access to the collections it creates). No key can manage keys. |
| Progress measures | Raw measures only. Per card: FSRS stability, difficulty, retrievability now, review count, lapse count, last grade, next due time. Per collection: card counts, due count, reviews per day. The external client decides what "learned" means; the API never uses that word. |
| Operating budget | Everything runs on the Cloudflare Workers free tier: 100,000 requests a day, 10 ms CPU per request, 50 subrequests and 50 D1 queries per request, 5 cron triggers (checked 2026-10-21). |
| Framework | Saasaloy CLI `0.6.0` with the `base`, `api`, `database-d1`, and `auth` modules. No `admin`, `teams`, `multitenant`, billing, or `waitlist`. Saasaloy copies source into the repo and has no runtime import. Node 24.13+, pnpm 12, Turborepo. |
| Storage | Cloudflare D1 with Drizzle ORM and `wrangler d1` migrations. A review and its derived schedule are written in one D1 `batch()`. See [ADR 0001](../adr/0001-adr-store-data-in-cloudflare-d1-2026-10-22.md). |
| Owner login | Saasaloy `auth` email and password (Better Auth, sessions in D1). Sessions last 30 days and renew when used. Mindaloy's `auth.ts` sets `emailAndPassword.disableSignUp: true`, a known difference from the Saasaloy module. No reset email; the owner resets the password with a script. See [ADR 0002](../adr/0002-adr-owner-login-with-saasaloy-email-and-password-2026-10-22.md). |
| API keys | Built on an org-free mode of Saasaloy's `api-keys` module (`references: "user"`, no rbac dependency), which must ship upstream first. Scopes live in the Better Auth `permissions` column. Mindaloy adds an `api_key_collections` table and a `requireCollection` check, because Better Auth has no collection concept. A scope is fixed at issue time; change it by revoking and creating a new key. |
| API contract | Versioned HTTP JSON API under `/api/v1`. Mindaloy's routes use `@hono/zod-openapi` and serve `/api/v1/openapi.json`. Errors use stable codes such as `invalid_api_key`, `scope_missing`, and `collection_out_of_scope`. Internal fields stay out of the public contract. |
| Web app | Saasaloy's customer `app` module at `apps/app`, once it ships upstream. Phase 5 waits for it. |
| Ownership | Each collection has one owner. Every request checks ownership. Shared collections are deferred. |
| Cards | Stable server IDs. An external source ID and external card ID, unique within a collection. |
| Grades | Again, Hard, Good, Easy, mapped 1:1 to FSRS ratings 1 to 4 and stored as the integer rating. The API takes `again`, `hard`, `good`, `easy`. |
| Scheduler | `ts-fsrs` on the server only, with FSRS default parameters and desired retention 0.90. Each review points to a `scheduler_config` row holding the `ts-fsrs` version, weights, and retention. No parameter optimizer in the first release. See [ADR 0003](../adr/0003-adr-schedule-with-ts-fsrs-on-the-server-2026-10-22.md). |
| Due rule | A card is due when `due_at <= now`. For an interval of one day or more, the server moves `due_at` to the day start (04:00) of that local day in the owner's IANA time zone (`time_zone`, `day_starts_at_hour = 4` on the account). An interval under one day keeps its exact instant. A time zone change affects only future schedules. |
| Device clock | The server stamps `reviewed_at` with its own clock. A time sent by the client is ignored. |
| Review order | The server applies reviews in arrival order, one transaction per review. A review of a stale card revision is accepted and records the revision it saw. A repeated `client_event_id` returns the first result. |
| Card edits | A cue or key-point edit keeps the schedule and increments the card revision. `POST /api/v1/cards/{id}/reset` resets the schedule and writes a reset marker into the review history so replay stays deterministic. |
| Export and delete | Export uses the paginated list endpoints with an `include_archived` flag. Deleting a collection removes its cards and reviews. No account-delete endpoint in the first release. |
| Deployment | One Worker on `*.workers.dev` until the owner adds a domain. Batch create takes at most 50 cards per request. |
| Backups | D1 Time Travel (7 days on the free plan) plus a weekly `wrangler d1 export` the owner runs by hand, listed in the release checklist. |
| API tests | Saasaloy's Vitest setup (`app.request()` with the `cloudflare:workers` stub), with a local D1 through Miniflare where a test needs SQL. |
| Browser tests | Playwright for the review process in Phase 5. Use accessible locators. |
| UI rules | No house rules or approved reference exist. #2 approves mobile layouts, keyboard behavior, and a visual reference before UI implementation. |
| Saasaloy issues | The owner files the upstream issues drafted under [Saasaloy dependencies](#saasaloy-dependencies). No agent files them. |
| Attended phases | Phases 5 and 7 stay attended. Phases 2, 3, and 4 can run unattended once their blockers clear. |

## Approach

One Saasaloy-generated Worker serves the API and the web app, with one D1 database. The Worker owns cards, reviews, and schedules. The web app uses the same `/api/v1` operations as external clients. This keeps scheduling and permissions consistent.

The first release is online-only. Offline review was the larger alternative; it adds sync, provisional schedules, and a reorder rule for delayed reviews, so it moves to a later release. Lesson planning stays in external systems.

Two pieces of the stack must ship in Saasaloy before the phases that need them: an org-free API key mode (Phase 3) and the customer `app` module (Phase 5).

### Phase 1: approve scope, architecture, and visual direction (#1, #2)

Attended: The owner approves the first-version scope, account model, technical decisions, and visual reference.

- Confirm whether offline phone reviews belong in the first release. Settled: no.
- Confirm whether the first deployment supports one owner or public account registration. Settled: one owner.
- Choose the web and API frameworks, account provider, and initial deployment target. Settled: Saasaloy, its email and password auth, and Cloudflare Workers.

Done when: The plan records the owner's choices, the grade mapping, and a dated visual approval. DESIGN.md records the approved UI rules.

### Phase 2: define the data model and API contract

- Define accounts, collections, cards, immutable reviews, derived schedules, and `scheduler_config`.
- Give cards a cue, key points, archive state, revision, and optional source reference.
- Define list, create, read, update, and archive operations for collections and cards.
- Define due-card queries, review submission, review history, progress queries, and the schedule reset operation.
- Define API key creation, scope selection, revocation, and last-use information, using the scope names in the settled decisions.
- Define pagination, `updated_since` cursors, request validation, error codes, and retry behavior in the OpenAPI specification.
- Define idempotent card creation through external IDs. Define idempotent review submission through client event IDs.
- Define card revision checks and arrival-order review handling.

Done when: The contract covers an external client's complete create, review, and progress process. Examples include unauthorized access, a key outside its collection scope, duplicate requests, and conflicting card edits.

### Phase 3: build storage, access, and card management

Blocked on: Saasaloy draft 1 (org-free API key mode).

- Create the application with Saasaloy CLI `0.6.0` and the `base`, `api`, `database-d1`, and `auth` modules, then add `api-keys` in its org-free mode.
- Turn off sign-up in `auth.ts` and add `pnpm db:seed:owner` and the password reset script.
- Measure the CPU time of sign-in in Workers Logs and record the number in this plan. If sign-in exceeds the 10 ms free-tier limit, stop the phase and report it.
- Add the `api_key_collections` table and the `requireCollection` check. Return each new key value only when the user creates it.
- Enforce ownership and key scopes before reads and writes. Limit request rates, and cap batch create at 50 cards.
- Implement collection and card operations with external ID support and revision checks.
- Keep credentials and typed answers out of routine request logs.

Done when: API tests create a card through a scoped key and read it through its owner's session. Another account cannot access it. A key cannot reach a collection outside its scope. A revoked key fails, and repeated external IDs do not create duplicate cards. The recorded sign-in CPU time is within the free-tier limit.

### Phase 4: implement reviews and scheduling

- Implement `ts-fsrs` and the grade mapping in one server module, reading parameters from `scheduler_config`.
- Store each accepted review with its event ID, card revision, server review time, grade, scheduler config, and optional typed answer.
- Persist the review and derived schedule in one D1 `batch()`.
- Apply the day start rule for intervals of one day or more.
- Rebuild a card's schedule from its reviews and recorded scheduler config, one card per request.
- Return due cards, review history, and the raw progress measures through the API.
- Preserve review history when a card is archived. Keep the schedule on card edits, and reset it only through the reset operation.

Done when: Tests confirm deterministic replay, duplicate protection, arrival-order handling of reviews from two devices, and the reset marker. Time zone tests confirm the 04:00 day start in at least two IANA zones.

### Phase 5: build the web review process

Attended: Waits on the #2 visual reference and the Saasaloy `app` module.

Blocked on: Saasaloy draft 2 (customer `app` module) and #2.

- Implement the approved collection list, card editor, review screen, and integration settings in `apps/app`.
- Show the cue before the answer. Let the user type an answer and reveal the key points.
- Let the user compare the answer with the key points and select a grade: Again, Hard, Good, or Easy.
- Show due counts, review results, and clear states for an empty queue or failed request.
- Let the user create and revoke API keys with visible operation and collection scopes.

Done when: A browser test creates a collection, reviews a card, reloads the page, and reads the saved result. The review process supports a phone viewport and keyboard use.

### Phase 6: prove external integration and prepare deployment

Attended: The owner creates the Cloudflare account resources, sets secrets, runs the restore test, and approves the deploy.

- Build a small documented API client that does not read the learning repository.
- Use it to create cards, update one card without duplication, and read review results.
- Document owner setup, API keys, examples, local development, and deployment.
- Document D1 Time Travel restore, the weekly `wrangler d1 export`, schema migration, and service rollback.
- Test a database restore into an isolated D1 database.
- Prepare a deployment configuration and a release checklist. Record phone checks that need the owner.

Done when: The independent client completes the create, update, review, and progress process against a clean test deployment. The documented restore recovers cards and review history. The configuration is ready for a separate deployment approval.

## Saasaloy dependencies

The owner files these in `mimukit/saasaloy`, then links each issue number on the matching "Blocked on:" line below.

### Draft 1: api-keys: add an org-free key mode

The `api-keys` module fixes `references: "organization"`, so every key belongs to an organization and the module pulls in `rbac`, `multitenant`, `teams`, and `admin`. A one-owner app has no organization.

Add an owner option to `modules/api-keys`:

- With the option set to user, `apiKeyPlugin()` passes `references: "user"` to `@better-auth/api-key`.
- In that mode the module drops `dependsOn: ["rbac"]`, so it installs on top of `auth` alone.
- A user resolver replaces `apiKeyTenant` and returns the key's user and `permissions`.
- The scope guard checks the requested scope against the creating user, not an organization role.
- The prefix display, revocation, `lastRequest` update, and no default expiry stay as they are.

Done when `saasaloy add api-keys` with the user option installs on a base with only `auth`, creates a key whose `permissions` map holds the requested scope, verifies it on a bearer request, and refuses it after revocation.

### Draft 2: app: ship the customer app module

Mindaloy needs a logged-in product UI for a normal user, and `admin` admits only admin roles. Plan `docs/plans/0074-plan-agent-native-mvp-build-2026-10-21.md` describes an `app` module at `apps/app`; if that plan already tracks it, link that issue instead of filing this one.

The module should give a React SPA at `apps/app` on the `admin` stack (React 19, Vite, TanStack Router and Query, `packages/ui`), served as Workers static assets, using the `auth` session, with a route for a signed-in user that has no admin role.

Done when `saasaloy add app` gives a page a signed-in non-admin user can open and a signed-out user is sent to login from.

## Later releases

### Offline reviews and reliable sync

Moved out of the first release in phase 1. Not filed as an issue until the owner plans it.

- Cache the application and selected collections for offline use. Save pending reviews in IndexedDB before advancing the review screen.
- Show pending review counts and whether the displayed schedule is provisional.
- Sync pending reviews with stable client event IDs. Keep them until the server confirms receipt.
- Decide how the server orders delayed reviews from several devices and which clock it trusts for an offline review. This is deferred from phase 1.
- Separate cached data by account on the device.

### Personal scheduler parameters

Run the FSRS optimizer outside the Worker after about 1,000 reviews and save the result as a new `scheduler_config` row.

## Migration and rollback

The first release starts with an empty D1 database. It does not move or modify data in the learning repository. A future tutorkit client must use the public API and stable external IDs.

Add D1 migrations from phase 3. Test them before deployment. Export the database before a migration that can remove or rewrite data. Record which application versions support each schema.

A service rollback must preserve accepted reviews and must not replay them as new reviews. The offline release must keep unsent reviews until the server confirms them, and an application update must preserve that pending queue.

## Open questions

Resolved in phase 1 on 2026-10-22, except where marked deferred.

- Does the first release serve one owner, invited users, or public account registration? One owner.
- Does offline use remain a first-release requirement? No; it is a later release.
- Which login method, frameworks, deployment target, and operating budget should phase 1 approve? Saasaloy email and password, Saasaloy with Hono and D1, Cloudflare Workers, free tier.
- Should the app use three grades or expose the scheduler's full rating set? The full set of four.
- What counts as due across time zones, and how does the server handle an incorrect device clock? The day start rule; the server clock.
- How does the server order delayed reviews from multiple devices without losing accepted events? Arrival order for the online first release. The offline ordering rule is deferred to the offline release.
- Should a cue or key-point edit preserve the schedule, reset it, or require an explicit choice? Preserve, with a separate reset operation.
- Should the app retain typed answers by default? How long should it retain them? Yes, with no time limit.
- Which progress measures help an external system choose a learning phase? Who defines a learned condition? Raw FSRS measures and counts; the external client.
- Should the first client poll for changes, or does the first release need webhooks? Poll.
- Which API operations and collection scopes should agents receive by default? See the default API key scope decision.
- How does the owner export or delete account data, including retained review history? Paginated list export and collection delete. Account delete is deferred.
- Does Better Auth sign-in fit the 10 ms CPU limit of the free tier? Deferred to the phase 3 measurement.

## Non-goals

- No dependency on GitHub as the application database.
- No lesson authoring, course management, or built-in learning phase workflow in the first release.
- No AI grading, generated cards, or embedded model calls in the first release. External agents can create cards through the API.
- No offline review, dedicated MCP server, webhooks, or tutorkit adapter in the first release.
- No email sending, magic link, or password reset email in the first release.
- No shared collections, organization accounts, invited users, billing, or public card marketplace in the first release.
- No images, audio cards, cloze cards, or imports from other review products in the first release.
- No namespace registration, repository creation, application implementation, or production deployment under this planning task.
